# `with/push-notifications`

The node for an app that tells its users, by Web Push, of what happened on chain while they were away. The demo's "Notify me" toggle registers THIS DEVICE at push-notification-server and the account's TRIGGER ("a new greeting from anyone but me") at etherfold's trigger service; the trigger service follows an `etherfold run` of the greetings' processor, and on each match asks the push server to push to every device the account registered. A push delivered to the service worker is shown as a notification, or, when the app is open and focused, in the app's own notifications.

```
jolly-roger@main
├─ with/local-signer
│  └─ with/hosted-account
├─ with/embedded-chain
├─ with/indexer
├─ integration                [with/local-signer, with/embedded-chain]
├─ with/push-notifications    [with/indexer, with/local-signer]   ← here
└─ website
```

**Why from `[with/indexer, with/local-signer]`** (the plan's F2-1, the service-layers spec's `with/notifications`): the notifier follows the processor `with/indexer` defines, and both services verify one identity, the key set `@etherplay/connect` derives for the app (`account.keySet`: an Ed25519 signing key and an X25519 encryption key, derived from the local signer's origin key) and the wallet's signature authorising it (delegated-identity 0.2). Rather than from `with/local-signer` alone (the processor the notifier runs would live nowhere the app ships it).

**Why the notification is made in a service, not in the tab** (F2-2): the tab's indexer sees `MessageChanged` only while a tab is open, which is not push. The trigger service is etherfold's (ADR-0005: triggers run outside the indexer-server; ADR-0100: the reference service lives in etherfold as its own packages), the push server closes `/push` to anything but a token-holding service, and neither watches the chain itself.

**It degrades to its absence** (the spec's R2): with `PUBLIC_PUSH_SERVER`, `PUBLIC_VAPID_PUBLIC_KEY` or `PUBLIC_NOTIFIER` empty (the default in `web/.env`), the toggle is replaced by a line saying notifications are not configured, and everything else is `with/indexer`'s and `with/local-signer`'s.

**One account per device** (QA F21): push-notification-server keys a device by account, app and endpoint, so one browser could be registered for several accounts of the app and then received every one's pushes (with `with/messaging`, direct messages it cannot read there). This app registers with push-notification-server's `replaceOtherAccounts` (since 0.2) (`replaceOtherAccounts: true` in `$lib/context/app.ts`): enabling makes the device the current account's alone, the server removing its registrations for the app's other accounts in the same transaction. When the browser is signed in as another account than the one its device is notified for, the line says so ("This device is notified for another account (0x...), not this one") and "Switch it to this account" moves it, warning that the other account is then no longer notified on this device (its other devices keep their notifications). An app that wants one device notified for several accounts sets `replaceOtherAccounts: false`: the line then offers "Notify this one too" beside the switch, and, while on, names the other accounts with "Notify only this account". Signing out does not unregister the device: the next account to sign in is told, and switches it. A push that still arrives for another account (before the switch, or by design with the option off) says so when the app is focused: the greeting push names its recipient (`data.account`), and the app's own notification reads "For another account (0x1234...abcd): ..." (`$lib/push/recipient-label.ts`, QA F22). A notification the OS shows while the app is in the background is not labelled (the worker does not know who is signed in). A node whose pushes name their recipient elsewhere adds a reader with `pushRecipients.readRecipientWith` (`with/messaging`: missiv's `data.missiv.recipient`, QA F23).

## The pieces

|                | what                                                                                                                                                                                                         | where                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| the device     | @push-notification/client: the browser's push subscription against the VAPID key, registered with a request signed by the key set's Ed25519 key and the wallet's ownership signature                                     | `$lib/push/notifications.ts`, which wraps it                                  |
| the trigger    | `POST /greetings/subscriptions {address, domain, keySet, ownershipSignature, kind}` at the trigger service (the app's routes under its name, @etherfold/triggers 0.3), the same proof signed for its origin; renewed on every load (a trigger expires unless renewed, etherfold ADR-0012) | `$lib/push/notifications.ts`                                                  |
| what to notify | the kind `new-greeting`: a log of `MessageChanged` from anyone but the subscriber, rendered as a declarative push opening the demo                                                                           | `$lib/onchain/notifier/greetings.ts` (the app's, beside its processor)        |
| the payload    | the Declarative Web Push shape, declared once at the root, which push-notification-server's `DeclarativePushNotification` (the type its `/push` validates) is checked against                                | the root's `src/service-worker/push.ts`, the worker's push and click handlers |
| the services   | push-notification-server's Node.js platform, `etherfold run` of the greetings, the trigger service                                                                                                           | `web/notifier/`                                                               |

The wallet is asked AT MOST ONCE, and that is `@etherplay/connect`'s to ensure: the ownership signature is the account's `savedPublicKeyPublicationSignature` (a hosted account's from sign-in; a wallet's once it answered, which connect keeps on the persisted account, bound to the account and its key set; since connect 0.19 the message names the key set, and an account signed in before signs in once more), else `connection.getSignatureForPublicKeyPublication()` asks the wallet. The same signature serves the push server, the trigger service and missiv. A page load never prompts. The app's domain must be connect's signing origin (the page's, unless `signingOrigin` is set): `$lib/push/sources.ts` refuses to hand a service a signature for another message.

## What the node adds

- `web/src/lib/push/`: `notifications.ts` (`createNotifications`, the toggle's store: the device's status as the push client reports it, the trigger's, `enable`, `disable`), `sources.ts` (the account from the connection, the configuration from the environment, the worker's registration, connect's publication signature). The worker's push and click handlers are the root's (`src/service-worker/push.ts`, template-svelte).
- `web/src/lib/onchain/notifier/greetings.ts`: the greetings' trigger definitions, run by the trigger service; `web/src/lib/onchain/indexer/processor.bundle.ts`: the processor's `createProcessor` entry for `etherfold run`.
- `web/src/routes/demo/lib/NotifyMe.svelte`: the toggle, logic-less.
- `web/notifier/`: `reset-data.mjs` (each `pnpm start` clears the services' databases, below), `build.mjs` (the processor bundle, the source from the deployment, `serve.ts` bundled with the app's definitions), `serve.ts` (the three services, and a recording push sender for the e2e; the trigger service's registration API answers CORS for the app's origin itself, @etherfold/triggers 0.2), `keys.mjs` (the dev VAPID pair and push token, into gitignored `.env.local` files).
- Tests: `web/test/lib/push/` (the store against both services in process, the adapters, and `payload-type.test.ts`: the push server's payload type is the root's), `web/test/lib/onchain/notifier.test.ts` (the definitions load, and their push passes the server's `/push`), `web/test/notifier/reset-data.test.ts` (the start's reset), `web/e2e/tests/greeting-notifications.e2e.ts` (enabled, a greeting by another account, one recorded push, delivered to the worker and shown; a device registered for another account, said on the line and switched).

## What it changes from its stems

Each file is in `.offshoot-divergences`, under `[with/push-notifications]`, with its reason: where the stems meet (the composition, the demo page, `contracts/package.json`, the lockfile), the composition's notifications store and the demo's toggle, the dependencies, the env (`web/.env`, `web/.env.localhost`), the dev stack (`dev/zellij.kdl`: three panes), the e2e (`scripts/run-e2e-tests.sh` starts the notifier; a seventh account). The service worker is the root's: its push handlers, and the fix of a push posted to a focused page showing no title, went home to template-svelte, and the root's unwired `core/service-worker/push-notifications/`, which this node used to omit, is gone there.

## Running it

`pnpm start` opens the dev stack with three more panes: "push server" (it runs `pnpm --filter ./web notifier:keys` first, writing the dev VAPID key pair and the push token into `web/notifier/.env.local` and the VAPID public key into `web/.env.local`), "indexer (etherfold run)" and "notifier (trigger service)", which wait for the contracts' deployment (and the trigger service, for the indexer to listen: `web/notifier/wait-for-server.ts`). Ports 34005 (push server, `/api`), 34002 (etherfold) and 34006 (trigger service, this app at `/greetings`), each `NOTIFIER_*_PORT`; the services answer ONE app origin, `http://localhost:5173` (`NOTIFIER_APP_ORIGIN`), so open the app there. The service worker is off in `vite dev` unless `PUBLIC_ENABLE_SW_IN_DEV=true`, and without it there is nothing to subscribe (the demo's notifications line then says so, rather than asking to sign in), and with it on, dev registers a MODULE worker, which only Chromium-based browsers run (Firefox needs a build): try the toggle on a build (`pnpm --filter ./web build localhost && pnpm serve`, then `NOTIFIER_APP_ORIGIN=http://localhost:8080`). A real browser push goes through the browser's push service, so the dev machine needs the network.

Each `pnpm start` is FRESH: it opens a new local chain (same chain id, same contract addresses), so before zellij opens the panes it removes the notifier's databases from `web/notifier/.data` (`pnpm --filter ./web notifier:reset`, `web/notifier/reset-data.mjs`): the indexer's `greetings.db` and the trigger service's `triggers.db`, which would otherwise believe they are past blocks the new chain has not reached and push no greeting, and the push server's `push.db`, whose devices belong to the old run. So after a restart each device presses "Notify me" again (the notifications line shows it off). Attaching to a stack that is still running (`pnpm start` again while its zellij session lives) clears nothing. `NOTIFIER_KEEP_DATA=1 pnpm start` keeps the data; the dev keys (`web/notifier/.env.local`) are never removed. The e2e gives the notifier its own fresh folder each run.

The services' own logs (`named-logs`, which prints nothing without a sink) go to their pane at warn and above, through `web/notifier/log-sink.ts`: a push the browser's push service refused shows there as `[push-notification-server-api] Could not push (<status>): <body>`. `NOTIFIER_LOG_LEVEL` (`info`, `debug`, ...) shows more, `NOTIFIER_LOG` (names, `*`, `-name`) narrows which loggers print.

In production each service is the operator's, configured with its own keys: push-notification-server with `PUSH_TOKENS` naming this app's origin and the trigger service's token, and a trigger service hosting this app under a name (its `apps` entry, whose `delegatedIdentityVerifier` names this app's origin and the service's own public origin). The app then sets the three `PUBLIC_*` variables, `PUBLIC_NOTIFIER` being the service's origin and the app's name (`https://triggers.example/greetings`).

**Cascade ritual**: `with/indexer`, then `with/local-signer`, into this node. A conflict on `.offshoot-divergences` keeps both stems' sections and this one's; on `impersonate-addresses.json`, the superset.
