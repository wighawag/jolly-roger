# A synchronous, SSR-inert app context; readiness lives in store state

`createContext()` is synchronous and always returns a usable app context, on the client and on the server. Every system it composes must be constructible without browser APIs, falling back to its idle state when they are absent, and must start no IO until `start()` runs (which happens in `onMount`, so browser-only). Asynchronous work is never awaited in front of the context: it is represented as state inside the store that owns it (`connection.step`, `PollingValue.step`, `executor.status`, ...). A full-screen boot gate that awaits a promise before rendering anything is reserved for work without which no UI is meaningful at all (asset or WASM preload), lives at the boundary that needs it, and provides its own separate context.

## Considered options

- **Keep `createContext()` async behind a full-screen splash (the status quo).** Rejected: the entire layout, including routes that use no context at all, waits on it; and because the promise never resolves on the server, `prerender`/`ssr` produce the splash instead of the page, so the home hero and its `DefaultHead` metadata never reach the prerendered HTML. The cost is paid on every load to preserve an `async` that has no `await` in it: `establishRemoteConnection` contains none, and `createConnection` is synchronous.
- **Split `Context` into a sync bucket and an async bucket behind a readiness gate.** Rejected: the layout cannot know which routed page depends on the async bucket without per-route configuration or a per-page wrapper component, and once children render on the server, prerendering a context-dependent route crashes the build. It also reintroduces exactly what ADR-0001 rejected, consumers handling "not ready yet", and its premise does not hold: the async subsystems already model readiness as state (see below).
- **Keep the context browser-only and add a separate SSR stub context.** Rejected: a second implementation of the same surface drifts from the real one. Making each service idle-on-server keeps one implementation and puts the knowledge of "what does this service look like with no browser" next to the service.
- **Await the connection at construction.** Rejected on its own merits: connecting is user-interactive, can take seconds, and can fail. `createConnection` deliberately returns synchronously in an `{step: 'Idle', loading: true}` state and fills in from `autoConnect` afterwards. Blocking on it would put a splash in front of a wallet handshake.

## Consequences

- The pattern already exists in the dependencies and should be followed rather than fought: `@etherplay/connect` returns its store immediately and resolves into it, and `synqable`'s storage interface is fully async (`load`/`save`/`remove`/`exists` all return promises) while `createAccountData` is called synchronously and hands back a usable store.
- Each service owns its own server behaviour. `createOfflineStore` and `getParamsFromLocation` already do this and are the reference implementations. `createPollingStore` must not start its loop off-browser (its value stays `{step: 'Unloaded'}`), the clock must not set timers, the tab leader must not claim a lock, the connection needs an inert variant, and the account store needs a no-op storage adapter.
- The prerendered HTML becomes the real page. The home route ships its hero and its `DefaultHead` metadata as static HTML, which the splash previously replaced.
- The chrome renders in its disconnected state during SSR, and hydration matches because the client's first render is that same disconnected state. Readiness then arrives through the stores, as it already does today after connection.
- Configuration errors (`resolveBurnerWallet`, `resolveConnectionMode`, `resolveSignerRpc`) lose the `{:catch}` that surfaced them, so they become a fatal-error store on the context, rendered by the layout through the error display the app already has. Env-derived failures resolve at construction and therefore also appear in the prerendered HTML, which reports a misconfigured build on every page without needing a build-time validation step. Param-derived failures resolve in `start()`, so the server and the first client render agree.
- The splash is deleted rather than generalized: `AsyncContext.svelte` and `splash-loader.ts` go. Work that must finish before an experience is meaningful (game assets, WASM) is served better by an overlay driven by a progress store, rendered as a sibling with the app mounted underneath. An overlay expresses progress, supports staged branding with timing and skip, and lets the thing being loaded initialize concurrently instead of afterwards. That is this same rule applied one level up, and `../conquest-v1` already implements it that way. Supporting it requires nothing game-specific here, so it stays in the app that needs it.
- This decision reopens only if an asynchronous value is needed to construct an object's *identity*, and not merely to make that object *available*. The distinction is the whole point, and the in-browser node is the worked example: `embedded-eth-node` (as used by `../bomber-world`) exposes `createNode()` and `createWorkerNode()` as async, but `chainId` is an *option* rather than a discovery, and `SlimNode.request` is async by contract precisely so the same object works unchanged across a Worker boundary. So the chain identity stays static, and a deferred provider (`request: async (args) => (await ready).request(args)`) keeps every client constructible synchronously. What is genuinely runtime there is contract *addresses*, because deployment happens at boot, and that is a stepped `deployments` store rather than an async root. Availability belongs in state; only identity belongs in construction. Absent an identity-level async value, no future need justifies an async context: presentation is served by overlays and store state.
