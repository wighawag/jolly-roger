# `core/` is the part that does not know this app, and a test says so

A module belongs in `src/lib/core` if and only if it can be constructed, rendered and tested without the app's composed runtime. Concretely: **nothing under `core/` may import the BARE `$lib` specifier (`from '$lib'`) or anything under `$lib/context/`.** Everything that reads `getAppContext()` lives in `src/lib/ui`, beside the components that already do.

The bare-specifier part is load-bearing and must not be read as `$lib/*`: `core/` imports `$lib/core/ui/modal`, `$lib/shadcn/ui/button` and `$lib/core/utils/format/balance` constantly, and a rule banning the prefix bans the tree from compiling. The rule names two module paths, the app barrel and the app context, not the alias. The rule is held by a boundary test in the shape of `framework-boundary.test.ts`, with a `KNOWN_LEAKS` list that starts empty and a stale-entry check so the list cannot outlive the debt. `core/` keeps its shadcn and Tailwind content, because a default presentation is part of what this template gives you and removing it would be a different (and worse) template.

## The pressure that produced this

`core/` carries an implied promise that an adopter should not need to modify it, and a second, unstated promise that it is portable. Neither is written down anywhere except one line in `README.md` ("the reusable building blocks live in `web/src/lib/core/` and are independent of these routes"), and nothing checks either. So the question was which promise, if any, could be made true cheaply enough to be worth having.

The measurement answers it. `core/` holds 109 files. `with/local-signer` modifies six and adds eight; `with/hosted-account` modifies the same six and adds nothing; `website` modifies none. Cross-tabulate the modified list against what each module imports:

- Seven core files reach the app's composed runtime (`getAppContext` from `$lib`, or the `Context` type from `$lib/context/types`). **Four of the seven, 57%, are modified by a variant.**
- Of the other 102, two are modified (`connection/mode.ts` and `ui/modal/modal.svelte`), which is **2%**.
- Of the 15 core `.svelte` files importing `$lib/shadcn`, 4 are modified, and all 4 are among the seven above: the UI-kit signal is entirely confounded by the context signal.
- Of the 4 core files importing `$env/static/public`, **none** has ever been modified by any descendant.

A file that reaches the app context is about thirty times more likely to be edited by a variant than one that does not. That is not a coincidence, it is the mechanism: a component that reads the composed runtime must change when the composition changes, and the variant's composition adds `signerExecutor`, `signerBalance`, `topUp`, `delegation` and `hasLocalSigner`. Read the four diffs and every one is exactly that.

The corroborating evidence is what the variant ADDED to `core/` with nobody telling it where to put things: seven of its eight new files import nothing app-specific and are correctly placed; the eighth, `core/ui/confirm/ConfirmationModal.svelte`, imports `getAppContext`. An independent author following instinct produced this rule with one exception. That is the cheapest kind of rule to adopt.

## Considered options

- **Keep one `core/` and add the missing extension points the six modified files reveal.** This is the shape the prompt for this audit expected, and the evidence does not support it. It is right for exactly one of the six: `ConnectionFlow.svelte` appends two OAuth buttons to a fixed sign-in list, and a `signInMethods` snippet would close that cleanly. For the others, there is no slot that would help. `InsufficientFundsModal` grows a whole second remedy ("top up the in-app balance") whose existence depends on there being a second account; a "remedies" registry to make that a slot would be more machinery than the file it abstracts, and it would be machinery on `main` that only the variant ever uses. `AccountCannotSendModal` differs only in the wording of a dev-only hint, and a slot for a sentence of prose is not a design. `faucet-actions.ts` gained a `target` parameter and a return value, which is not a missing slot but a plain generalisation that should simply be backported. Rejected as the primary answer: it treats four symptoms of one cause, and leaves `core/` still meaning nothing.

- **Split `core/` by replaceability: portable logic and ports on one side, the default shadcn presentation over those ports on the other.** Rejected on the measurement. It optimises for a variant that swaps the UI kit, and no such variant exists in this tree or is planned; meanwhile it cuts across the line that actually predicts modification, since all four modified components import shadcn AND read the context, so the split would put them on the presentation side and leave the real problem untouched. It also costs the most of any option here (every `core/` component moves, every import updates, both live descendants take a large conflict) to buy a portability claim nobody has asked for. If a UI-kit swap is ever wanted, this remains available and the context rule below does not obstruct it.

- **Drop the claim, rename `core/` to what it is.** Genuinely tempting, and cheaper than any move: rename to `lib/platform` or `lib/toolkit`, delete the promise, done. Rejected because the promise is worth keeping rather than the name being wrong. Four descendant branches exist specifically to extend this template, and "which files can I edit without paying for it forever" is the single most useful thing the directory layout can tell their authors. Renaming answers a question nobody asked and leaves the useful one unanswered.

- **Make `core/` framework-free as well (no `$env`, no shadcn) and enforce all three at once.** Rejected as one decision, though the `$env` half is worth doing on its own merits (ADR-0006). Bundling them means the whole thing lands or none of it does, and the `$env` seam has a real cascade bill while this one is a supervised file move. The shadcn half is rejected outright: 15 of 20 core components use it, this template descends from `template-svelte-shadcn`, and a default presentation is part of the inheritance.

- **Enforce with a lint rule (eslint `no-restricted-imports`) instead of a test.** Rejected for consistency rather than capability. The repo already has two boundary rules and both are vitest files that run in `pnpm test:unit`, both carry their reasoning in a doc comment a reviewer reads, both guard themselves against a vacuous pass, and one of them needs to follow a QUESTION across files in a way a lint rule cannot. A third rule in a third mechanism would be the first place someone looks and does not find.

## Consequences

- **Seven files move**, from `core/connection/ConnectionFlow.svelte`, `core/transaction/{AccountCannotSend,InsufficientFunds,ErrorDetails,InFlightRequests}Modal.svelte`, `core/ui/faucet/FaucetButton.svelte` and `core/ui/faucet/faucet-actions.ts`, into `lib/ui/`. That directory already holds eight components that call `getAppContext()`, so they arrive among their own kind rather than founding a new category.

- **`core/` becomes statable in one sentence**, which is the entire point: nothing in here knows this app. An adopter can keep it. A variant author knows where a new file goes. A reviewer has a rule to cite.

- **The rule needs two named exceptions, and naming them is part of the decision.** `$lib/deployments-store` is imported by five core modules; it is generated per app but has one shape, no descendant has ever modified any of those five files, and converting it to a capability would touch five core modules plus every consumer to solve a problem nobody has. It is sanctioned by name, with that reason, in the style of `wallet-activity-boundary.test.ts`'s `SANCTIONED` list. `core/connection/executor.ts` imports `type {TransactionMetadata}` from `$lib/account/AccountData`; that one is type-only and should eventually become a generic parameter, so it goes in `KNOWN_LEAKS` with an expiry rather than being blessed.

- **`core/connection/mode.ts` stays exactly as it is, and stays modified by descendants.** `TARGET_STEP` is documented as the one line a descendant changes, it is in source rather than env so the comparison stays statically analysable and the unused branch can be eliminated, and its two historical conflicts were both one-line resolutions. A working extension point that happens to be spelled as an edit is not a boundary violation. The rule proposed here does not touch it, and that is deliberate.

- **`core/ui/modal/modal.svelte` is not fixed by this and should not be.** Its divergence is two independently invented layer schemes meeting in a cascade, already recorded in `work/notes/observations/two-layer-schemes-met-in-the-cascade.md`, whose fix is to backport `core/ui/layers.ts` and its test to `main`. Different problem, different note, do it separately.

- **The consequence I like least: this does not reduce merge cost much.** Those six files account for 13 conflict events out of 65 across 44 merges, none conflicting more than twice, and moving them does not make the variant stop editing them, it only moves where the edit lands. The merge tax lives in `context/index.ts` (6 conflicts on its own) and the demo routes (8 between two files). **This ADR should be sold as making a claim true, not as making merges cheaper.** Anyone justifying it on merge cost will be disappointed and will have picked the wrong item off the list.

- **The cascade has to be supervised once.** Four of the seven moved files are modified on `with/local-signer`, so git's rename detection has to carry those modifications across a move. It handles that well when content is otherwise similar, which it is, but the resolution must be read rather than trusted. Budget half a day on `main` and half a day at `with/local-signer`. `with/hosted-account` inherits it for free (24 merges of its own, three conflict events, all in the lockfile and `package.json`). `website` touches none of these files. So the honest cascade cost is **one contested merge, not four**.

- **A near miss worth stating: the test must watch imports, not paths.** `wallet-activity-boundary.test.ts` learned this the hard way, when its rule watched a file and the fifth consumer had moved to another one. Here the equivalent trap is a core module that takes the context as a PARAMETER rather than importing it, which is fine and is exactly what `faucet-actions.ts` does today via `Pick<Context, ...>`. That is still an import of `$lib/context/types` and the rule still catches it, which is right: a module typed against this app's context is a module that knows this app, whether it fetches it or is handed it.

- **The relocation must be a pure `git mv` commit with no content change.** Four of the seven files are modified on `with/local-signer`, and rename detection is what makes those modifications reapply at the new path instead of arriving as a delete plus an add, which would either drop them silently or force a hand re-application under merge pressure. Move in one commit, fix the importers in the next. Editing a file's contents in the same commit that moves it is gambling on similarity scoring for no reason.

- **The descendants were audited before landing this, and the answer is eight files across two branches.** DONE 2026-08-22, recorded in `work/notes/findings/descendant-audit-for-the-core-boundary-rule.md`. Seven on `main`, exactly one more anywhere else (`with/local-signer`'s `core/ui/confirm/ConfirmationModal.svelte`, inherited unmodified by `with/hosted-account`), zero extra on `website`, and zero on `stem/main`, which structurally cannot violate the rule because it has no app context. The extra file needs no new decision: it reads `getAppContext()` and renders a pending question, it is rendered from `AcrossPages.svelte` like the others, and its logic half (`confirmation.ts`, importing only `svelte/store` and `core/ui/overlay`) stays in `core/`. Same split, same fix, in the same cascade. This mattered: without the audit the boundary test would have failed at merge time on a file this ADR never examined, and the decision would have been made a second time, on a branch, under merge pressure, by whoever was holding the cascade. That is how a rule acquires an exception nobody agreed to.

- **Part of `core/` is co-owned with the parent template, and this ADR only governs jolly-roger's part.** `stem/main` (`template-svelte-shadcn`) carries `core/notifications/`, `core/service-worker/`, `core/utils/web`, `core/utils/tailwind` and a `core/config.ts`, and drift flows both ways (`da43158`, "core: sync framework-agnostic drift from jolly-roger"). The seven files this ADR moves are all jolly-roger's own (connection, transaction, faucet), so the MOVE is unambiguously ours. The RULE is a different matter: it would be worth more at the home, where every descendant of the parent would inherit it, and landing it only here means the parent can reintroduce a violation that we then have to catch at merge time. Land it here first because that is where the evidence was gathered and where the violators live, then propose it upstream as a separate change rather than assuming it travels. Note also that the parent's `core/config.ts` is NOT a configuration module in ADR-0006's sense; it is the parent's equivalent of this repo's `lib/index.ts` app barrel, moved out of `core/` here by `91ef28b` ("make core indepenent") precisely because it imported `$app/environment`. That relocation is the same instinct as this ADR, five hundred commits earlier, and it is the strongest evidence that the rule is one this tree already believes.

- **The detector must not police prose, and must be shown not to.** A naive search for `getAppContext` matches `core/capabilities/README.md` and `core/capabilities/define.ts`, both of which mention it in documentation explaining the capability-versus-context distinction. Documentation that explains the boundary is the last thing a boundary test should punish. Both existing boundary tests already avoid this (they match import CLAUSES rather than occurrences, and `wallet-activity-boundary.test.ts` carries explicit guard-the-guard cases after a first version flagged a file whose only import was the sanctioned one). The new test inherits both properties or it is worse than nothing: a rule that fires on comments teaches people to stop writing comments.
