# Overlays split by where their visibility lives; navigation is a capability

An overlay is either a **system overlay**, whose visibility is derived from domain state (`$connection.step`, `$balanceCheck.step`, `$errorDetails`), or a **view overlay**, whose visibility *is* the state. System overlays survive navigation, never push history and never touch the URL: the condition that opened them is still true on the next page, so closing them would be a lie and they would reopen anyway. View overlays are declared through a registry and come in exactly two named kinds, with no default: a **content overlay** shows a thing, is bound to a URL param, survives reload, and is keyed by an id whose payload the view resolves live; a **prompt overlay** asks about an action in flight, is never in the URL, is never restored, and dies with a navigation. Every view overlay closes on route change centrally, and opening one pushes one ephemeral history entry per level so the back gesture unwinds the stack. All of this sits on a `navigation` capability (`$lib/core/capabilities`, see ADR-0001) whose SvelteKit adapter is the only module allowed to import `$app/navigation`.

The bug that produced this decision: opening the pending-operation modal on `/transactions/` and clicking an address inside it navigated the page and left the modal floating on top of the new one. The modal's state was a module-level global (`src/lib/ui/pending-operation/pending-operation-store.ts`), so nothing tied it to the route it was opened from. That is not a local defect. This is a template, so whatever mechanism answers it is the mechanism every app built on it will copy, and the app already had a second, hand-rolled answer to the same question: the navbar drawer closes itself with a `showMenu = false` in an `onclick` on each of its four links (`src/lib/ui/navbar/navbar.svelte`).

## Considered options

- **A `closeOnNavigation(close)` helper each overlay calls.** Rejected: it makes the correct behaviour opt-in, so in a template the default is the wrong one and the failure is silent. It is the same shape as the four hand-written `showMenu = false` lines, one forgotten call away from the reported bug, and it teaches adopters that navigation-awareness is each feature's problem.
- **One mechanism with `closeOnNavigate` / `backCloses` / `urlBound` booleans.** Rejected: the flags allow combinations that make no sense (a system overlay that closes on navigate and instantly reopens, a confirmation dialog restored from a URL with no action to confirm), and a flag defaults to something, which reintroduces the silent-wrong-default problem. Two named constructors carry the same information and cannot be combined into nonsense.
- **URL-bound as the default for every view overlay.** Rejected on the evidence: of the five view overlays in the app today, one is content (`PendingOperationModal`) and four are prompts (`ConfirmDismissDialog`, `GasPricingForm`, `ConfirmCancelDialog`, the navbar drawer). A URL-bound prompt is actively harmful, not merely useless: restoring "Are you sure you want to cancel this transaction?" after a reload restores a question about an action whose in-memory context is gone, `GasPricingForm` additionally carries a half-entered gas price and a `minGasPrice` derived from a live operation, and the URL is shareable, which turns a destructive confirmation into a link. Making the kind explicit at declaration asks "should this survive a reload?" at the only moment the answer is obvious.
- **Ephemeral as the default, with URL binding as an opt-in.** Rejected for the mirror-image reason: apps built on this template will hold more content panels than this one does, and a content overlay that silently fails to be addressable is a missing feature nobody notices. Neither kind is the default; the constructor names the kind.
- **Intercept the back button and dismiss instead of navigating, so no history entry is needed.** Rejected because the platform does not permit it. `popstate` is not cancelable, and the Navigation API explicitly cannot cancel a `traverse` navigation (it can only intercept a same-document one), while Firefox and Safari have not fully shipped that API, so the platform where the back gesture matters most does not offer it at all. The only available "block" is to let the pop happen and then restore position, which is visibly wrong under iOS's interactive swipe-back and is the history trap this ADR rejects for non-dismissable overlays. It also fails outright in the case that matters most: a user who deep-lands on a page, opens an overlay and presses back is traversing to another origin, which nothing can intercept or restore. `pushState` is not a workaround for a missing veto, it is what creates an entry of our own for back to consume, and `pushState('')` leaves the URL byte-for-byte unchanged.
- **A shared history entry for the whole overlay stack (`replaceState`), so back closes everything at once.** Rejected: it needs a special case the moment a prompt opens from inside a content overlay, since it would have to either replace that overlay's entry and break its URL binding or exempt itself. One entry per level has no special cases, matches what the back gesture means everywhere else on the platform, and the extra entries are bounded by a stack that is two deep in practice.
- **The registry renders overlays through a single outlet.** Rejected for now: it buys lazy loading and an explicit stacking order, but it puts component references into overlay definitions and drags the framework back into the layer this decision is trying to keep portable. The stacking problem is better solved by making the layer order explicit than by centralising rendering. The silent-no-op risk it would have removed is handled instead by a dev-only warning when an overlay is opened with no live renderer.
- **A per-context-member overlay instance (`context.overlays.pendingOperation`, declared in `createContext`).** Rejected: every new overlay would mean editing `context/index.ts` and `context/types.ts`, and that tax is exactly the incentive that produced the module-level global in the first place. The registry instantiates lazily from a colocated description, in the same define/use shape as capabilities.
- **Reorganising the tree so logic sits in framework-free directories mirroring the component hierarchy.** Rejected as a way to reach framework portability: portability is determined by what a module imports, not by where it sits, and mirroring costs a large refactor while buying layout symmetry. The enforceable version is a rule, `no $app/* import outside the adapter layer`, over a surface that is already small and enumerable (22 import sites across 17 files, of which the leaks into `lib/core` are `service-worker/index.ts`, `capabilities/route.ts`, `utils/web/path.ts`, `metadata/Head.svelte` and `transaction/AccountCannotSendModal.svelte`).
- **Blocking unload from the overlay ("this modal is open, so warn before leaving").** Rejected: the dangerous condition is an in-flight wallet request that the app has no record of, not a modal. Tying the guard to the overlay silently loses it in every case where the request exists without that UI, including after the escape hatch described below. The guard belongs to the navigation capability and is registered by domain state.

## Consequences

- Closing on navigation stops being a feature author's problem. It is implemented once, over the registry, and every view overlay an adopter adds later inherits it. The navbar drawer's four `showMenu = false` lines are deleted rather than duplicated a fifth time.
- Back closes overlays, including on mobile where there is no ESC. There are then four dismiss paths already wired in `core/ui/modal/modal.svelte` (ESC, click-outside, the X button) plus back and programmatic close, and the load-bearing invariant is that **all of them funnel through the overlay's single `close()`**, which conditionally drops the history entry: it pops only when our token is still the current entry, so a programmatic close that arrives after the user has navigated on cannot yank them off a page they chose. Any dismiss path that bypasses `close()` leaks an entry and makes back appear dead. This is the main implementation risk and it lives in one place, so it is testable.
- **Navigating away with an overlay open leaves its entry behind, so the first back press from the destination lands on it rather than on the previous page.** Same URL, overlay closed, and a second back leaves. We take this deliberately: the entry sits below the one the router just created, and popping entries out from under a user mid-navigation is not ours to do. The same bargain applies when an overlay opened from a deep link is closed, since there is nothing beneath the entry the user arrived on to return to: the URL is rewritten where they stand, and back returns to how they arrived with the overlay addressed again.
- **We give back exactly the entries we pushed, never one more.** An overlay that ADOPTED the entry the user arrived on cost no history entry, so counting a closing range rather than our own entries traverses one too deep, which in a real browser walks out of the app entirely (reload with the inspector open, raise a prompt, let the action succeed). The fake browser in the tests deliberately records an over-deep traversal rather than clamping it, because clamping is what let this pass its tests once.
- Reload with a prompt open leaves an entry whose state is gone, so the first back press appears to do nothing. This is inherent to shallow routing (SvelteKit documents that `page.state` is not applied on the first page a user lands on, including after a reload) and is accepted deliberately. "This overlay must survive a reload" is precisely the signal that it is a content overlay instead.
- Non-dismissable overlays push nothing. Every one of them today is a system overlay in `ConnectionFlow.svelte` (waiting for wallet connection, waiting for signature, invalid chain), each `openWhen={$connection.step === ...}` with no `onCancel`, and pushing an entry for them would force a choice between making them dismissable, which contradicts their contract, or trapping the user's back gesture.
- The pending-operation modal becomes a content overlay keyed by operation id, which removes the module-level global and, by construction, a second latent bug: both openers pass a frozen `OnchainOperation` value (`OperationCard.svelte:156`, `toastConnector.ts:125`), so a modal open while its transaction is included, finalized or resubmitted currently keeps showing the state from the moment it opened. Addressing state instead of copying it fixes the reported bug and the staleness with the same change.
- **A content overlay must read the URL from `window.location`, never from `page.url`.** SvelteKit's shallow routing changes the address bar without navigating: `pushState` calls `history.pushState` and assigns `page.state`, and deliberately leaves `page.url` on the route the page is still showing. Since a content overlay's open state IS its param, reading `page.url` reports the URL as it was BEFORE the overlay was opened, so the overlay is judged absent from the URL and closed the instant it opens: the address bar changes and no modal appears. This was the first bug found in real use, it is invisible to unit tests that fake the browser, and it is the reason the driver is the only place allowed to answer "where are we".
- **A content overlay resolves its payload from data that arrives asynchronously, so "not found" has to be two answers.** Account data is restored from storage only once an account is known, so an item that is not there yet is UNKNOWN, not gone. Collapsing the two closes the overlay during the gap and strips the id back out of the URL, which breaks exactly the case the URL binding exists for: reloading, and following a link to one. The view therefore models `loading` and `missing` separately and only acts on `missing`. Any content overlay added later has the same obligation.
- The navigation capability becomes the one place that knows how this app navigates, which is worth more here than in a normal SvelteKit app because there are currently two routing worlds: `createRouteHandler` rewrites dynamic routes to hash URLs on path-based IPFS gateways, and `routes/explorer/lib/location-param.ts` hand-rolls `hashchange`/`popstate` listeners to read them. Those listeners fold into the capability so there is one location stream, and content-overlay params are read and written through it so they survive the hash rewriting (`path?query#hash`).
- `guardUnload` is decided but deliberately not built, because it has no consumer until the transaction work below and a template should not ship untested API surface. When it lands it fires only for `willUnload` navigations (reload, tab close, leaving the origin) and never for in-app navigation, which loses nothing in an SPA.
- The prompt shown before unload is a courtesy, never the safety mechanism. Operations are only recorded on `transaction:broadcasted` (`account/connectors.ts:31`, `AccountData.ts:129`), so between dispatching `eth_sendTransaction` and receiving the hash the app has no record of a transaction that may already be in the mempool, and no dialog survives a tab crash, an OS kill or a force-quit. The real fix is to persist a pending-request record (account, chain, expected nonce, intent) *before* dispatch and to reconcile by nonce afterwards, in the terms `core/connection/nonce-cache.ts` already uses, with the outcome modelled as **unknown** until reconciled and never as failed or rejected. This is what makes the escape hatch that `connection-flow.ts:285` already has a TODO for safe to build: a user who stops waiting must never cause the app to record a rejection it did not observe.
- ADRs live on the `work` orphan branch, which the citations in the code now say explicitly, since a reader on `main` who follows `docs/adr/...` finds nothing.
