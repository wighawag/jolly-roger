# The in-flight ledger answers a DIFFERENT question from `wallet.pendingRequests`, so the upstream fix changed the precedence and not the existence

`core/connection/wallet-activity.ts` reconciles three sources into one answer about what the wallet is holding. Two of them are `wallet.pendingRequests` (the connection library's list) and `$inFlight.dispatching`/`$inFlight.prompting` (the app's own count of sends it has made and not had answered). The app's count used to OUTRANK the list everywhere, for one stated reason: the list went missing. `@etherplay/connect@0.10.0` fixed that. The ledger stays, every preference that read it stays, and each one is now justified by one of two durable reasons instead: a send signed by a key the app holds itself is not a wallet request and can never appear in a list of them, and the ledger starts a beat before the wallet has been handed anything. Exactly one thing changed materially: the ledger may still raise the wallet-action modal, and it may no longer put the WALLET'S words on it.

The bug being retired: every wallet-state rebuild inside `createConnection` asserted `pendingRequests: []`, which erased an outstanding request permanently, because the list is written only on request events and the next event for a request is the one that ends it. The transition is `connect()`, reached by an ordinary path: a send against a locked wallet raises the connection flow, so `connect()` runs while the wallet is still holding the transaction. A real locked-Rabby session logged `pendingRequests: 0` alongside `inFlight.dispatching: 1` (`work/notes/observations/wallet-action-required-modal-not-seen.md`). 0.10.0 copies the live list from the provider wrapper at every rebuild.

## Considered options

- **Delete the ledger and read `wallet.pendingRequests` alone, now that it is trustworthy.** Rejected, and it is the move this ADR exists to prevent, because the code said "the list goes missing" in five places and a reader who fixes that upstream will reasonably conclude the whole thing was scaffolding. It is not. A dispatch signed by a local signer sends with no dialog and no wallet involved, so it is structurally absent from a list of wallet requests, and it is still outstanding, still losable by a reload, and still something the user can be trapped by. `with/local-signer` and `template-commit-reveal` are built on that path. Deleting the ledger silently removes the escape hatch and the unload guard for every transaction those apps send.
- **Keep the ledger but demote it everywhere to a fallback consulted only when the list is empty.** Rejected, because it is right in one place and dangerous in another, and applying it uniformly is how this module's bugs have historically been introduced. See the `outstandingRequestKind` consequence below: there the ledger must keep outranking the list, and 0.10.0 made that MORE true rather than less.
- **Keep the ledger and change nothing but the comments.** Rejected as not quite honest. It would leave the wallet-action modal saying "please confirm the request in your wallet" during the window between `handle.dispatched()` and the wallet actually receiving `eth_sendTransaction`, which is a window in which no wallet has been asked anything. `in-flight-store` already moved that counter once for exactly this reason, from `record()` to `dispatched()`, and could not move it far enough: viem still reads a chain id, a nonce and a gas estimate through the same provider before the wallet sees a thing. Against a slow public RPC that is seconds of a false instruction.
- **Move `handle.dispatched()` after the send actually reaches the wallet.** Rejected, and it is the fix that would remove the problem at its source rather than wording around it. There is no hook for it: `guardDispatch` hands the whole call to viem, which decides when to issue `eth_sendTransaction`, and the record must exist BEFORE the send or a reload in between loses the transaction, which is the entire point of the ledger. Reachable only by having the library report a request the moment it is issued, which is what `pendingRequests` already is: hence the option below, which is the one taken.
- **Let the LIST decide what the modal says, and the LEDGER decide only that something is up.** ACCEPTED. Before 0.10.0 the two were inseparable, because an empty list meant either "the wallet has not been asked yet" or "the wallet was asked, then the list was erased", and nothing here could tell those apart, so the loud wording had to cover both. An empty list now means exactly one thing, so the block and the claim can be split: the modal still opens on the app's own dispatch, and says "Getting your transaction ready" rather than speaking for a wallet that has not been asked.
- **Ignore `purpose` and `account`, the two fields 0.10.0 added.** Rejected. `account` is what makes an outstanding request's owner visible at all, and it exists because a request can now OUTLIVE the wallet state it started under: the user may switch wallet or account while one is pending, the upstream list is not per-wallet, and the wrapper does not mark or drop a request when the wallet is swapped underneath it. Without comparing it, the modal tells the user to approve in whichever wallet is current, which after a switch cannot answer. `purpose` names what a library-originated signature is for, and a delegation grants a browser key authority to act for the account, which is both worth naming and precisely the shape a phishing prompt takes.
- **Type `purpose` as the upstream union in `ConnectionStateSnapshot`.** Rejected. The union is expected to grow and a purpose only selects flavour text, so an unrecognised one must fall back to `kind` rather than break a build in an app that would have coped. `kind` IS pinned to the upstream union, deliberately, because a third kind changes what the app must SAY about danger (a signature approved late is untidy, a transaction approved late moves funds) and that deserves a compile error rather than the last branch.
- **Remove the `WaitingForSignature` branch in `ConnectionFlow.svelte` now that library signatures are announced.** Rejected, and not attempted. `requestSignature` still signs OUTSIDE the wrapper on purpose, so that sign-in does not open two modals at once: the component opens one dialog from that step and another from the pending-request path. Upstream records the coupling in its own `docs/adr/0001-wallet-requests-are-announced-through-the-wrapper.md`.

## Consequences

- **`offersEscapeHatch` keeps its ledger clause, with a smaller job.** For a wallet dispatch it is now redundant: the request is in `pendingRequests` for its whole life, so `!canDismissConnection` already answers true. What it still covers alone is a locally-signed send and the beat before the wallet has anything. Both are moments where the user is genuinely stuck and the library, correctly, reports nothing.
- **`outstandingRequestKind` keeps its ledger clause AND its precedence, which the fix made more load-bearing rather than less.** It decides whether stopping waiting may call `connection.cancel()`, and cancelling with a transaction in flight is the disconnect-and-lose-the-transaction bug this module was built after. A send the app signed itself is invisible to the list by construction, so reading the list first would let a signature sitting beside it answer `'signature'` and take the cancelling branch. That pairing used to be near-hypothetical and is now ordinary, because the same release routed `getDelegation` and `getSignatureForPublicKeyPublication` through the wrapper: library signatures are announced where before they opened a wallet with nothing behind them. Pinned by `does not let a visible signature outrank a silent transaction`.
- **`shouldPromptForWalletAction` keeps its ledger disjunct and loses its ledger WORDING.** This is the material change. The boolean is worth keeping: the user should not be clicking around a form whose send is already committed, and this is the moment the escape hatch has to be reachable from. The claim is not, for the window described above.
- **The modal's words are now a field on `WalletActivity` rather than a literal in the component.** `promptCopy`, beside `escapeCopy`, decided by `walletPromptCopy`. This is the boundary rule working as intended: a consumer that needs a sharper answer adds a field to the derived value instead of reaching around it for a primitive, which is what let five consumers drift far enough apart to cancel a connection with a transaction in flight. `test/wallet-activity-boundary.test.ts` is unchanged, because nothing new needed to be sanctioned.
- **The modal is no longer always titled "Wallet Action Required".** It names a delegation, a public-key publication, a transaction or a signature, and says which account a request is waiting on when that is not the connected one. The generic title survives as the fallback for a request whose kind cannot be read, never as an error. `e2e/tests/escape-hatch.e2e.ts` matches the transaction wording rather than the old fixed title, which makes it a stricter assertion than before: it now asserts the app is speaking FOR THE WALLET, which it may only do when the wallet really is holding something.
- **`pendingRequestIds` was silently repaired without changing.** `stopWaitingForWallet` feeds it into the stopped-waiting set, so an emptied list meant it recorded no ids and the per-request suppression did nothing; the modal stayed down only because `stopAwaiting()` had zeroed the ledger. The mechanism designed in `createStoppedWaiting`, give up on THIS request and keep prompting for the next, works as written for the first time.
- **The window is finally covered end to end.** `e2e/tests/escape-hatch.e2e.ts` parks a transaction, locks the wallet, re-enters the flow through `ensureConnected()` (which is what the demo page's Send awaits first, and where the `forceConnect` path actually lives, unlike bare `connect()`), and asserts the library's list still holds the request AND that the modal, the escape hatch and the unload guard all stay up, then that they clear when the wallet answers. Pinned back to `@etherplay/connect@0.7.1` it fails with `expected 1, received 0`. `e2e/fixtures/stalling-wallet.ts` gained a real listener registry and `lock()`/`unlock()` to make the transition reachable: `on` was a no-op, so no test could stand inside a wallet-state rebuild, which is a large part of why the bug shipped.
- **The unload guard did not move and did not need to.** `hasUnansweredRequest` reads `dispatching` alone and never consulted the library's list, so the fix does not touch it. A silent transaction between dispatch and hash is exactly as losable as a loud one.
- **Two upstream problems were visible from here, and the ledger is what hid them from users. Both are now closed by 0.11.0, one of them by being refused.** `wallet: undefined` sidestepping the fix is genuinely fixed: `pendingRequests` moved off the wallet object onto the connection and is stamped inside the single `set()`, so the states that build no wallet report it too. The `connect()` versus `ensureConnected()` asymmetry turned out to be deliberate and is now written down upstream as three distinct promises, with `unlock()` as the narrow remedy for a locked wallet; what made the picker path look destructive was the first defect, not the asymmetry. See the update block on the observation note, and the migration consequence below.
- **The app reads `connection.pendingRequests`, and `^0.11.0` is a floor rather than a preference.** Accepting `state.pendingRequests ?? state.wallet?.pendingRequests` would restore the exact ambiguity the move removed, in which an empty answer means either "nothing is outstanding" or "this state has no wallet to ask". So the app reads only the new field and fails loudly against an older one, which `e2e/tests/escape-hatch.e2e.ts` demonstrates rather than asserts in prose.
- **`ConnectionStateSnapshot`'s own doc comment was making a claim that was false, and now is not.** It said a rename upstream fails the typecheck here. That is true for `step`, which is `Pick`ed from the real union, and was never true for any field this app re-declares: they are all optional, so the real `Connection` stays assignable after upstream drops or renames one, and the app would quietly read `undefined` for a request the wallet is genuinely holding. That is this module's own failure mode arriving through the type system. `pendingRequests` cannot simply be `Pick`ed, because its real element type has four required fields and the tests here pass deliberately partial fixtures, so the shape is asserted separately instead. Verified by narrowing the snapshot's `kind` and watching it fail, rather than by reading it and believing it.
- **The "not yet asked" branch of `walletPromptCopy` has narrowed twice, which is the argument of this ADR playing out.** It once had to cover an erased list (0.10.0) and then a list that vanished with the wallet object (0.11.0). What is left is the one case no library fix can reach, the window between `handle.dispatched()` and the wallet actually being handed the send. It keeps its both-readings wording anyway, because an upstream regression is cheaper to survive than to detect.
- ADRs live on the `work` orphan branch, as ADR-0004 records, so citations in the code say so explicitly.
