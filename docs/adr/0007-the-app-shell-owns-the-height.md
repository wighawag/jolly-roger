# The app shell owns the height, so a page's `h-full` is the viewport minus whatever chrome is up

`routes/+layout.svelte` mounts one **app shell** (`core/ui/AppShell.svelte`): a `h-dvh` flex column, padded by `var(--navbar-height)` for a navbar that is `fixed`, holding the condition bars as fixed-size rows and the page in a `flex-1 min-h-0` region tagged `data-app-content`. The region is therefore EXACTLY what the chrome leaves, so a bar appearing SHRINKS the page instead of pushing it down, and `h-full` inside the region means "the viewport minus whatever chrome is up right now" without the page knowing which bars exist or how tall they are. The document remains the scroller. WHICH bars exist is a list (`ui/chrome.ts`), not markup, so a descendant adds one without touching the layout. The shell itself is one import and may be replaced; the contract is enforced by `e2e/tests/layout-shell.e2e.ts` measuring `[data-app-content]`, not by preventing replacement.

The bug that produced this decision came from a descendant. `template-commit-reveal` needed its game route to fill the screen exactly and wrote `h-[calc(100dvh-3rem)]`, with the comment "`3rem` is the navbar's own `h-12`; there is no variable for it to track". That subtracts the navbar and forgets the bars, so any one of the four conditions (offline, no RPC, stale nonce cache, a dispatch in flight) made the document taller than the viewport by the bar's height, and `GameHud` is `absolute inset-0 ... justify-between`, so its bottom row went under the fold. The casualty is the phase clock, which the page's own comment calls the thing a player needs to see. That is not a local defect: the trap was armed in the TEMPLATE, where `h-screen` plus a bar is a page taller than the screen, so it was armed once for every descendant and the first one to need a full-height surface tripped it.

## Considered options

- **Leave it to each page: `h-[calc(100dvh-Xrem)]` where a route needs to fill the screen.** Rejected, and it is the status quo being replaced. It requires every such page to know the chrome's total height, which is not a constant: it is the navbar plus however many of four conditions are live right now. The descendant that wrote it subtracted only the navbar, which is the correct answer for zero bars and wrong for every other case, and the failure is silent because the page looks right until a condition fires. It also spelled the navbar height a fifth time, in a second repo, having correctly observed that no variable existed to track.
- **`min-h-dvh` on the shell instead of `h-dvh`.** Rejected on measurement, and it is the option that looks obviously better. It keeps the chrome pinned across the whole document (measured: navbar stays at top 0 through a 1200px scroll where `h-dvh` puts it at -648), but it makes the shell's height indefinite, so the region's height is indefinite, so a percentage height inside it resolves to `auto` and `h-full` collapses. That is the entire contract, so this option cannot be taken. It is recorded because it is the first thing anyone will suggest.
- **Make the content region the scroller (`overflow-y-auto`), an app-shell scroller.** Rejected, with the price measured rather than guessed. It pins all chrome forever and keeps `h-full` exact, but: back-navigation scroll restoration stops working entirely, because SvelteKit saves and restores WINDOW scroll (measured: scroll to 250, navigate, go back, region `scrollTop` is 0); the scroll-to-top on forward navigation has to be reimplemented, and read as working only because the page tested had nothing to scroll; and `scrollbar-gutter: stable both-edges` has to move off `html`, or the navbar sits outside the region and misaligns with the content by a scrollbar's width. Two of the three land in `lib/kit`, so it is a framework-touching change rather than a CSS one. It remains the documented escape hatch for a descendant that wants permanently pinned chrome, and it owes that list back.
- **Keep the navbar `sticky top-0` inside the shell.** Rejected on measurement. A sticky element is pinned only while its containing block is on screen, and the shell is exactly one viewport tall, so a sticky navbar's travel is `100dvh - var(--navbar-height)`. The trigger is therefore not "a long page" but a page taller than roughly two viewports, which the HOME page reaches on a laptop window at half height or a phone in landscape: at a 348px viewport the navbar was 4px from gone at the bottom of the scroll. Losing the navigation is losing the way out. `fixed` has no containing block to run out of, and the shell reserves its space with the same `var(--navbar-height)` the navbar sizes itself with, so it stays one number.
- **Let each bar pin itself, as they did (`sticky top-[var(--navbar-height)]`).** Rejected on measurement. That says "pin me one navbar from the top", which is only true for the FIRST bar. With two conditions live, both pinned to the same offset and 37px of scroll put the second bar exactly on top of the first, permanently (measured: A=[48,85] and B=[48,85] from scrollY 60 to the end of the page). It also made pinning an invisible obligation on whoever adds the next bar, with a wrong default. One sticky element around the group has no arithmetic to get wrong, and a bar becomes a plain `{#if condition}<div>` that knows nothing about pinning.
- **Make the bar group `fixed` too, driving the shell's padding from a `--chrome-height` written by a ResizeObserver.** Rejected for now, and this is the closest call in this document. It would remove the remaining concession entirely: chrome pinned forever, document still the scroller, `h-full` still exact, for roughly fifteen lines. It is rejected because it turns the padding from a constant back into a computed number, which is the class of thing this whole decision exists to delete, and because the concession it removes is not reachable in this app (see Consequences for the rule and the numbers). If a descendant with genuinely long pages and two habitual conditions finds it, this is the option to take, in preference to the app-shell scroller.
- **Keep the chrome as markup in `routes/+layout.svelte`.** Rejected on measurement. That file is the most-edited in the template, and it says so about itself. A three-way merge of the shell into `template-commit-reveal` conflicted on 127 of 257 lines, 107 of them in a single block, because the shell both wrapped the chrome and re-indented it and git cannot match a re-indented block against an edited one. With the chrome as a list the steady state (both sides on the shell, each adding a bar of its own) is 14 lines across 2 hunks, both "keep both sides": an import and a list entry.
- **Put the chrome LIST in `core/`, as `layers.ts` does.** Rejected: which bars an app has is the app's own business, and a descendant dropping the nonce-cache bar or adding "round closing in 20s" must not be editing a `core/` file to do it. `core/ui/chrome.ts` holds the shape, `ui/chrome.ts` holds this app's list. The height contract stays in `core/` because it is not an app's business.
- **Make the shell unreplaceable, on the grounds that a swappable shell can re-arm the bug.** Rejected, and an earlier draft of the code comment wrongly claimed this was the design. A descendant may need a genuinely different shell (an app-shell scroller, a sidebar down one side) and one import is the right cost. What a replacement does not get is silence: the e2e measures `[data-app-content]`, not `AppShell`, so it tests whatever shell is mounted. Replaceability without a contract is what produced the originating bug; replaceability with a measured contract is just flexibility.
- **`svh` or `lvh` instead of `dvh` for the shell's height.** Rejected, reasoned rather than measured, and flagged as such because a real mobile browser's URL-bar behaviour is not reproducible headless. `dvh` is the dynamic viewport, so the shell resizes as the mobile URL bar retracts, which is a reflow storm for exactly the canvas consumer this decision serves. The reason it is still right: retraction requires SCROLLING, and the canvas route does not scroll (its container is `overflow-hidden` and exactly the region's height), so the consumer that would suffer never triggers it. Meanwhile `svh` is always the SMALL viewport, so on any page where the bar is already retracted (after a scroll, or after navigating to a short page) the shell would be shorter than the visible area and leave a strip of background at the bottom, breaking "the region ends at the fold" at the only moment the shell is fully on screen. `lvh` fails the mirror case by hiding content behind the bar. Revisit with a real device if a descendant reports thrash on a page that both scrolls and holds a full-height surface.

## Consequences

- **A page that wants the screen writes `h-full` and gets it, whatever chrome is up.** That is the contract, and it is what `template-commit-reveal`'s `/play` becomes. Measured at a 348px viewport: region 300 with no bars, 263 with the offline bar, and a `h-full` probe inside reports exactly the region in both cases.
- **A bar SHRINKS the page rather than pushing it down.** Nothing goes under the fold when a condition fires, and nothing re-lays-out below the fold when it clears. This is what earns the bars the right to sit in flow at all, and `ui/in-flight/sending.ts` draws the same line from the other side: transient action feedback floats, durable conditions take space.
- **The document is still the scroller**, so native scroll restoration on back, the mobile URL bar retracting, pull-to-refresh and `scrollbar-gutter` are all unchanged. Verified: scroll to 200, navigate away, return, window scroll is 200.
- **THE CONCESSION, exactly.** The bar group's containing block is the shell's content box, which runs from the navbar's bottom to the fold, so its travel is `viewport - navbar - group`, which IS the content region's height. The group therefore stays pinned for the first `region` pixels of scrolling and then slides up under the navbar. Equivalently it detaches only on a page whose content exceeds TWICE the region. Nothing in this app reaches it: the tallest page is 690px against a 1030px threshold at a 600px viewport, and provoking it took four simultaneous bars on a 490px window. Pinned by test.
- **Each bar costs twice, so watch the scaling before adding a fifth.** A bar shrinks the region by its height AND lengthens the document by its height, so the detach threshold falls by twice the bar. The chrome therefore leaves soonest exactly when there is most of it. The navbar does not share the limit because it is `fixed`.
- **`scrollbar-gutter: stable both-edges` becomes load-bearing for the fixed navbar.** It puts the gutters inside `html`'s padding box, so the containing block a fixed element resolves against is already inset, and `w-full` on the navbar lines up with the content beneath it (measured: 1250 wide at left 15 in a 1280 viewport, no horizontal overflow). Removing that line silently makes the navbar a scrollbar wider than everything under it.
- **Adding a bar is one line in `ui/chrome.ts` plus a plain component.** A bar is zero-prop and self-gates from the app context, so the list says only that it exists and where it sits. The one gate that is a ROUTE question rather than a domain one (the RPC bar is irrelevant on the home page, which reads no onchain data) is a `when` on the list entry, keyed on route id rather than pathname so it stays base-path independent under IPFS.
- **`--navbar-height` drops from five spellings to two.** The navbar's own height and the shell's padding. `top-12`, the four per-bar offsets and the descendant's `3rem` all go.
- **This must cascade, and `/play` is part of the same pass.** A descendant that merges the shell without changing `h-[calc(100dvh-3rem)]` to `h-full` gains nothing: the game div is still `100dvh - 48` inside a region that is already `100dvh - chrome`, so it still overflows by the bar's height and the HUD still goes under the fold. The shell is necessary and not sufficient.
- **A descendant that replaces the shell must also inherit `layout-shell.e2e.ts`, or it has replaced the contract with nothing.** This is the weak point of "the tests are the enforcement": the enforcement is only present where the test is. A descendant that keeps the shell is fine either way; one that writes its own and drops the test has no guard at all, and nothing in the code can tell it so.
- ADRs live on the `work` orphan branch, as ADR-0004 records, so citations in the code say so explicitly.
